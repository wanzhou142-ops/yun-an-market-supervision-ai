# 06 · 资产优化与切换性能

> 对应需求：场景切换偶尔卡顿 → 定位原因并解决。

## 一、实现流程

### 1. 定位根因

切换卡顿**不是动画逻辑问题**，而是**资产过大压垮 GPU**：
- 背景原图 `4032×3024`（约 12MB）
- 人物原图 `1344×3168`（约 15MB）

切换时浏览器要解码 + 合成这些超大位图，主线程/光栅化线程被占满 → 掉帧。

### 2. 瘦身脚本（[`tools/optimize_assets.py`](../../tools/optimize_assets.py)）

- 背景：`cover` 裁到 `1920×1080`
- 人物：等比缩到高 `1200px`
- 总体积 `15.1MB → 2.25MB`（约 -85%）

### 3. 前端预解码（`page.tsx:471-483`）

```ts
(Object.keys(SCENE_META) as Scene[]).forEach((s) => {
  const m = SCENE_META[s];
  [m.avatar, m.photo].forEach((src) => {
    const img = new Image();
    img.src = src;
    preloaded.push(img);                 // 持引用防 GC 回收解码结果
    void img.decode().catch(() => {});   // 提前解码，切换时直接上已解码位图
  });
});
preloadedRef.current = preloaded;
```

- 只在**视频模式空闲期**后台下载+解码，切场景时走缓存、零网络延迟。
- `decode()` 把"位图解码"也提前完成（仅设 `src` 只保证下载，解码仍要等首次绘制，那一下会卡）。
- 持引用防止被 GC 回收导致解码失效。

### 4. 过渡期渲染优化（`globals.css`）

- `will-change: opacity, transform` 只挂在**过渡中的图层**（`bg-cross-in/out`、`avatar-cross-in/out`），提前提升为独立合成层，避免切换首帧临时建纹理掉帧（`globals.css:84-94, 138-148`）。
- 过渡期关掉透明 PNG 的 `drop-shadow`（`.avatar-cross-in .avatar-img { filter: none }`）：双层同时按 alpha 算轮廓阴影是掉帧主因之一（`globals.css:153-156`）。

## 二、技术栈

| 技术 | 用途 |
|------|------|
| Python PIL `cover` 裁剪 + 等比缩放 | 资产瘦身（一次性） |
| `HTMLImageElement.decode()` | 提前解码位图，避免切换时卡 |
| 引用持有 `preloadedRef` | 防止解码结果被 GC |
| CSS `will-change` | 提示浏览器提升合成层 |
| 过渡期临时关 `drop-shadow` | 减少双层阴影计算 |

## 三、踩的坑

1. **误以为是动画的问题**：第一反应是调动画时长/缓动，但卡顿在切换"首帧"。真正原因是位图太大。定位靠"切场景时 DevTools Performance 面板看主线程被谁占满"——结论是图片解码。

2. **只设 `src` 不够**：以为预加载 `src` 就完事，实际首次绘制才解码，那一帧仍卡。`decode()` 才是把解码提前的关键。

3. **解码结果会被 GC**：`new Image()` 设完 `src` 若不持引用，JS 引擎可能回收，导致缓存失效、切换又重新解码。必须 `preloadedRef.current = preloaded` 持引用。

4. **透明 PNG 阴影很贵**：`drop-shadow` 按 alpha 逐像素算，双层过渡时双倍开销。过渡期临时关掉，肉眼无差但性能大好。

## 四、学习建议

- **性能问题先定位再改**：不要凭直觉调参。浏览器 DevTools 的 Performance / Memory 面板是定位"谁在卡"的标准工具。本项目卡顿来自"大图解码"，不是 JS 逻辑。
- **decode() 与 src 的区别**：`<img src>` 触发下载；`img.decode()` 返回一个 Promise，完成后位图已就绪。做图片密集型切换（画廊、大屏）一定要预 `decode()`。
- **`will-change` 是"提示"不是"魔法"**：长期给大量元素开 `will-change` 会占内存；正确用法是**只在需要动画的短暂期间**挂上。本项目只在过渡层用，正是好实践。
- **资产规范前置省性能**：与其运行时优化，不如上游就把图裁到合适尺寸（本项目 `optimize_assets.py` + 出图规范 650×1300）。
- 延伸：浏览器渲染管线（JS → 样式 → 布局 → 绘制 → 合成）、栅格化线程、合成层。
