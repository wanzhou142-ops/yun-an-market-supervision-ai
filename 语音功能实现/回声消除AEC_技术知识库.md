## 一、回声从哪来

数字人（大屏）自己播报回答时，声音从**喇叭**播放出来，会：
1. 直接**空气传播**进麦克风（声学回声）；
2. 或被电路耦合进采集通路（线路回声）。

结果：麦克风同时录到「用户说的话」+「大屏自己刚播的声音」。如果不处理，Vosk 会把大屏自己的播报也当成语音去识别 → 自激、乱答。

---

## 二、AEC 是什么、怎么消

**AEC = Acoustic Echo Cancellation（声学回声消除）**。核心思路：
- 已知「我正在播出的参考信号 `r(t)`」；
- 估计「喇叭→麦克风这条路径的冲激响应 `h`」（用**自适应滤波器**，经典算法 NLMS / 频域 FDAF）；
- 从麦克风信号里减去 `h * r(t)` 的估计回声，得到「只剩用户人声」的干净信号。

难点在于**双讲（Double-Talk）**：用户和大屏同时说话时，AEC 容易把用户声音也误减掉。所以需要 **DTD（双讲检测）** 来判断此刻该不该更新滤波器。

## 三、你们为什么关掉 AEC

这是本项目的一个**刻意取舍**，不是疏漏：

| 考量 | 说明 |
|---|---|
| 保真优先 | Vosk 是小模型（43MB），对波形畸变敏感。AEC 处理后波形被改，可能伤识别率。保留原始波形更稳。 |
| 半双工规避 | 展厅是「按钮触发 + 轮流对话」，不需要边听边说。前端用 `speaking` 半双工锁：AI 播报时（`speaking=true`）直接 `return` 不开麦，播完再听。回声根本进不来。 |
| 更简单 | 不上 AEC 就少一个会出问题的模块，交付更稳。 |

> 代码位置：`dify-frontend/app/page.tsx` 的 `speaking` 锁——`if (speaking) return` 拦住播报期间开麦，这是你们替代 AEC 的机制。**唤醒=屏幕按钮**（点「开始互动」触发，视频模式一直播、无人不中断），不靠说"安安"唤醒；语音里的"安安"仅作闲聊词，不再拦截导航（设计 v2）。半双工锁 + 屏幕按钮共同确保回声根本进不了麦克风。

## 四、AEC 的几种实现（将来要上时选）

| 方案 | 特点 | 备注 |
|---|---|---|
| **WebRTC AEC3** | Google 开源，行业标杆，内置 NLMS + 非线性处理 + 舒适噪声 | 做全双工首选 |
| **SpeexDSP** | 轻量，老牌，C 实现 | 嵌入式友好 |
| **RNNoise** | 把降噪和 VAD 做在一起（RNN） | 顺带解决噪声问题 |
| 云厂商内置 | 讯飞/阿里/腾讯/百度的流式 ASR 接口里 AEC 是内置的 | 用在线 API 时不用自己写 |

## 五、何时该启用 AEC

满足以下任一条件，就该把 AEC 打开：
1. **切在线 API + 做全双工**：像小智实体机器人那样「边听边说」，半双工锁就不够了，必须靠 AEC 防自激。
2. **远场麦克风阵列**：展厅若换远场阵列麦（非当前手持近讲麦），回声路径更复杂，AEC 必要性上升。
3. **用户要求打断**：希望用户能在 AI 播报中途插话（barge-in），就必须全双工 + AEC。

当前项目（手持近讲麦 + 按钮触发 + 半双工）**不需要 AEC**，关掉是对的。

## 六、一句话记忆

> 回声 = 大屏自己听到自己。消回声有 AEC，但你们用「半双工锁」替代了它——因为只有轮流说话，回声根本没机会进麦克风。等哪天要做「边听边说」，再把 AEC（WebRTC AEC3）请回来。
